SIMLYTICS STREAMLIT APP STRUCTURE · v1 SPEC

Page structure for the web interface

How the five designs map onto a Streamlit multipage app on top of the existing db/, queries/ and stats/ packages. Nothing here changes the ingest or derivation pipeline — the app is a read-only consumer of the same SQL the notebook uses.

1 · File layout

app/
  Home.py                  # entry: st.navigation + league/season pick + season rail
  pages/
    1_Session.py           # 2a shell: Result / Timeline / Passing / Pit / Pace tabs
    2_Time_frame.py        # 3a: range picker + metric builder + heatmap
    3_Head_to_head.py      # 3b: two-driver compare
  lib/
    data.py                # cached query runners (the only place SQL is executed)
    filters.py             # season rail, range-mode picker, metric multiselect
    charts.py              # altair builders (position-by-lap, box, heatmap, radar…)
    fmt.py                 # ms→s, 0-based pos→1-based, colour scale per driver
  .streamlit/config.toml   # dark theme tokens

Three pages, not eight — the tabs inside 1_Session.py are st.tabs, so switching tabs never re-runs the session picker or re-queries the result table.

2 · Data layer

One function reads a .sql file and returns a DataFrame; every page calls it and nothing else. Route through db.connection so the app obeys the existing single-access-point rule.

# lib/data.py
from pathlib import Path
import pandas as pd, streamlit as st
from db.connection import connection

QUERIES = Path(__file__).parents[2] / "queries"

@st.cache_resource
def _conn():                       # one pooled connection per server process
    return connection().__enter__()

@st.cache_data(ttl=600, show_spinner=False)
def run_sql(name: str, **params) -> pd.DataFrame:
    sql = (QUERIES / name).read_text()
    return pd.read_sql_query(sql, _conn(), params=params or None)

@st.cache_data(ttl=600)
def sessions(season_id: int) -> pd.DataFrame:   # powers the season rail
    return run_sql("session_list.sql", season_id=season_id)

Cache keys are the file name plus params, so a season-wide query is computed once and shared by all three pages. A "Refresh data" button in the sidebar calls st.cache_data.clear() — that is the whole story after an ingest.

NEW SQL THIS APP NEEDS
session_list.sql — subsession_id, round, track, date, laps, sof, caution count per season (season rail + selectbox).
race_result.sql — the finishing table for one subsession, with net green passes and median pit Δ joined in (2a's main table; today's driver_standings.sql is season-grained).
race_running_order.sql — lap_num, cust_id, position, gap_ms, gap_pct, flags for one subsession (position-by-lap lines, running order at lap N).
race_events.sql — union of passes, pit stops, caution/restart laps as one ordered feed (2b's event list).
race_pass_matrix.sql — passer × passed counts for one subsession (3c matrix).
green_laps.sql already covers the pace tab; add a subsession_id filter clause.

3 · State & deep links

Every selection lives in st.query_params as well as st.session_state, so a URL is a shareable view — the thing a league needs when someone posts "look at lap 27".

The one rule that keeps this sane: the range picker writes a list[int] of subsession ids into state, and every downstream query takes that list. Round / date / last-N / hand-pick are four editors for the same value, exactly as drawn in 1e.

4 · Page by page

Home.pyLeague / season entry
Sidebar: league selectbox → season selectbox → the season rail (st.radio with a formatter, or a column of st.buttons for the card look) → "Season-wide" links. Body redirects straight to the newest session with st.switch_page; the sidebar block is defined once here and imported by every page from lib/filters.py.
1_Session.pySession home — designs 2a, 2b, 3c, 3d, 3e
Header strip of st.metrics (laps, SOF, cautions, green passes, lead changes) from session_list.sql, then st.tabs([...]):
Resultst.dataframe on race_result.sql with selection_mode="single-row" (row click → sets a and jumps to head-to-head) + column_config.ProgressColumn for pit Δ. Right column: mini position chart, pit bars, season-impact box.
TimelineAltair line chart of race_running_order.sql with a lap selection_point bound through st.altair_chart(on_select="rerun"); caution bands as a layered mark_rect. The selected lap drives the running-order table, the event feed slice and the flag strip. Shift-drag stint select = an interval selection on the same chart.
PassingAltair heatmap (race_pass_matrix.sql), stacked bars by flag (passing_by_flag.sql filtered to the race), conversion table (passing_conversion.sql), restart bars (passing_restarts.sql). Matrix cell click writes lap and switches to Timeline.
Pit cyclespit_cycle_by_race.sql as the stop table; the window strip is an Altair mark_rect of in/out laps per driver. st.toggle("Show outliers") flips the is_outlier filter — the query already exposes it, so this is a client-side mask, no re-query.
Pacegreen_laps.sql → Altair mark_boxplot normalized to the race median, stint line chart, and a median-vs-spread scatter reusing stats/driver_features.py's skew-normal fit.
2_Time_frame.pyRange + metric builder — design 3a
Sidebar: mode segmented control (st.segmented_control) → st.select_slider for rounds, st.date_input for dates, st.number_input for last-N, st.multiselect for hand-pick; then a metric st.multiselect whose selection just picks columns off one wide frame — join driver_standings, passing_score and pit_cycle_ranking once on cust_id and slice, never re-query per metric. Body: sortable table, driver × round heatmap, points progression (driver_points_progression.sql). The two option toggles map to driver_standings_drops.sql and the outlier mask.
3_Head_to_head.pyTwo-driver compare — design 3b
Two driver selectboxes (pre-filled from a/b query params), sharing the same range picker. Mirrored metric bars are one Altair bar chart per side with reversed x scale; the radar comes from passing_score.sql's z_* columns (already emitted for exactly this re-weighting use); the field scatter is the same frame with the two drivers highlighted. Meetings row needs a passes query filtered to the pair.

5 · Theme

The palette from the designs, as Streamlit config — set it once and the widgets, tables and Altair defaults follow.

{{ themeToml }}
#1b2024 #212830 accent gain caution loss

One driver → one colour, assigned once per season in lib/fmt.py and reused by every chart and table accent, so a colour means the same driver on every page. Altair over Plotly here: selections round-trip to Python via on_select, which is what makes the timeline scrub and the matrix drill-down work at all.

6 · Build order

01Data layer + season rail. lib/data.py, session_list.sql, sidebar. Proves connection reuse and caching before any chart exists.
02Result tab. race_result.sql + the metric strip. The whole app is useful at this point.
03Time frame page. Reuses existing season SQL unchanged — cheapest big win after step 2.
04Timeline tab. The one genuinely new query set (race_running_order, race_events) and the only place selection plumbing matters.
05Passing, Pit, Pace tabs — each one query plus one or two charts.
06Head-to-head last: it is mostly re-slicing frames the other pages already cache.
